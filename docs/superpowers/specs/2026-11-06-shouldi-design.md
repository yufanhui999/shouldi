# ShouldI（帮我选）设计文档

- 版本：v1.0（MVP 基准）
- 日期：2026-11-06
- 状态：待评审
- UI 基准：仓库根目录 `index.html`（可交互原型，视觉与交互以此为准）

---

## 1. 概述

### 1.1 一句话定位

**把纠结发出来，让大家投票、给意见——你参考着做决定，再把结局记录回来。**

### 1.2 核心理念

选择困难的人把问题交给群体**参考**，而不是**让权**：

- 平台角色是「投票 + 意见 + 参考」，决定权始终在提问者手里
- 每个帖子沉淀为一条真实决策案例（回访机制），后来人可以搜索借鉴
- 词库里禁止出现「劝、立誓、宣判、服从」等主导性词汇（见决策记录 D12/D13）

### 1.3 名称

- 中文（暂定）：帮我选
- 英文 / 仓库名：**ShouldI**（每篇帖子本身都是一句 "Should I…"，疑问姿态 = 求参考而非让权）

### 1.4 目标用户与成功标准

目标用户：面临选择的大学生/年轻职场人（求职、消费、旅行、情感、日常琐事）。

上线 30 天定量验证指标（默认值，可调）：

| 指标 | 目标 | 度量方式 |
|---|---|---|
| 真实发帖数（非运营贴） | ≥ 30 | posts 表统计（排除 admin 标记） |
| 投票数 | ≥ 300 | votes 表 |
| 带理由的意见数 | ≥ 100 | votes.reason 非空计数 |
| 结果回访数 | ≥ 3 | outcomes 表 |
| 单帖平均参与人数 | ≥ 8 | votes / posts |

验证成功 → 注册个体工商户、申请正规类目转正；验证失败 → 复盘归档，沉没成本为一次完整全栈实践。

## 2. 核心场景

| 场景 | 类型 | 示例 |
|---|---|---|
| A. 重大抉择 | 低频高价值 | 应届生：A 公司 22k·9116 vs B 国企 9k·965 |
| B. 计划型选择 | 中频 | 预算 1000 元，元旦去北京/上海/成都 |
| C. 临场微决策 | 高频、LBS | 商场 B1 十家饭店午饭选哪家（选项最多 10 个） |

三类场景同一套结构（背景 + 2~10 选项 + 投票 + 意见），不区分产品形态。

## 3. 产品决策记录（Decision Log）

开发过程中不得擅自推翻以下决策；如需变更，先更新本文档并注明原因。

| # | 决策 | 结论 | 原因 |
|---|---|---|---|
| D1 | 场景范围 | 重大 + 微小抉择都要，不做分类 | 单条信息流，选题多样性即刷的动力；分类等内容量起来再加 |
| D2 | 卡片信息 | 不显示题号、不显示发布时间 | 卡片极简；附近 tab 显示距离 |
| D3 | 选项数量 | 2~10 个；卡片只显示票数前 3 名 + 「共 N 个选项」 | 兼顾修罗场与临场十选一 |
| D4 | 身份 | 默认匿名（系统生成匿名号），投票意见流不显示身份 | 敏感内容（薪资/公司/感情）敢写真话 |
| D5 | AI | 不出面对话，仅后台可用作审核辅助 | 人工社区的差异化；JuryNow 用 AI 冒充人类导致核心承诺崩塌 |
| D6 | 回访 | 核心差异化：提问者事后记录最终选择 + 感受 | 沉淀为可搜索的决策案例库；听劝文化已验证「回来更新」行为存在 |
| D7 | 投票动线 | 必须先投票才显示比例、才可发表意见；意见自动带「投给了X」立场标签 | 参与钩子 + 立场先于观点；广场是观众席（比例可见），详情是当事人席 |
| D8 | 供给动机 | 靠围观顺手投票 + 经验分享；积分/等级/互惠后置 | 冷启动期激励无效且催生垃圾内容 |
| D9 | 转发即求助 | 分享卡片 = 帖子本身（标题+选项+实时票数），群里点开即投 | 增长内建于机制（钱包请等等验证） |
| D10 | 命运转盘 | 保留，详情页「不想纠结？让命运决定」 | 中性随机兜底工具（小决定类产品验证的刚需），无「服从」含义 |
| D11 | 附近 | 附近/最新/热门三 tab；首次进附近弹位置授权（用途声明：仅算距离，不展示给他人） | 微决策时效半径仅数百米；**降级方案**：wx.getLocation 权限申请不通过则附近 tab 改为按城市 |
| D12 | ~~立誓+截止宣判~~ | **砍掉** | 「立誓/宣判/服从」词汇过重，合规风险 + 有替人决定色彩，脱离参考定位 |
| D13 | ~~「听劝/劝」文案~~ | **否决** | 平台是投票+意见+参考，不是劝人干什么的平台 |
| D14 | 载体 | 微信小程序（个人主体，工具类目），uni-app 保留一键出 H5 的能力 | 已知类目风险；H5 为对冲预案 |
| D15 | 后端 | **完整自建前后端 + 管理后台**（本决策，2026-11-06） | 用户要求完整项目；内容需人工审核，「不是所有问题都能随意发布」 |
| D16 | 内容审核 | 两级：msgSecCheck 机审通过即发布；命中风险/被举报 → 人工队列 | 兼顾发布即时性与审核义务 |
| D17 | 冷启动 | 公域内容引流（小红书/知乎/贴吧），回访案例是天然爆款素材 | 已选定的增长路径 |

## 4. 功能规格（MVP）

### 4.1 用户端（微信小程序）

**广场（首页）**

- 三个 tab：附近 / 最新 / 热门
- 最新：按发布时间倒序；热门：按投票总数倒序（MVP 无算法）
- 附近：定位 5km 内、72 小时内发布的帖子，按距离升序；未授权/无定位内容时显示引导空状态
- 帖子卡片：标题 + 票数前 3 名选项的比例条 + 「N 人参与 · M 条意见」+ 回访徽章（如有）
- 下拉刷新、触底分页

**帖子详情**

- 头部：匿名提问者 · 状态（投票中/已回访）· 时间
- 背景描述
- 回访块（如有）：置顶展示「最终选了 X · N 个月后」+ 感受引文
- 选项区：未投票时点选即投（「投它」）；投票后解锁比例条、各选项票数、「你的选择」标记
- 意见区：每条 = 立场标签「投给了X」+ 文本 + 赞；排序：点赞数倒序
- 底部常驻：意见输入条（未投票时提示「先投一票，才能发表意见」）
- 「不想纠结？让命运决定」→ 命运转盘（全屏、扇区=选项、可重转）
- 「转发到群 · 点开就能帮我投」→ 转发卡片（标题 + 选项 + 实时票数）

**发布**

- 标题（≥5 字，≤40 字）、背景描述（≤500 字）
- 选项 2~10 个，动态增删
- 匿名说明前置；提交 → msgSecCheck → 通过即上广场 / 风险进人工审核（提示「审核中」）
- 成功页立即请求「回访提醒」订阅消息授权（一次性订阅，当场授权错过不再）

**我的**

- 我的求助：状态（投票中/待回访/已回访）+「记录选择」入口
- 我投过的：帖子 + 「你投给了X」
- 匿名边界说明：「只有这里能看到这些都是你发的」

**回访**

- 入口 1：发布 7 天后订阅消息提醒 → 落地回访页
- 入口 2：「我的」待回访标记
- 内容：选最终选项（必填）+ 感受文字（必填，给后来人一句话）
- 提交后展示在帖子顶部，广场卡片出现「已回访」徽章

### 4.2 管理后台（Web，运营/审核用）

- 登录：管理员账号密码（DB 存储，bcrypt，JWT）
- 审核队列：待人工审核帖列表（机审风险/被举报），可查看全文 + 通过 / 驳回（驳回需填原因，用户端显示「未通过审核」）
- 帖子管理：全量列表、搜索、下架（下架后用户端不可见，作者看到「已下架」）
- 用户管理：匿名号列表、发帖/投票记录、封禁/解封（封禁者不可发帖投票）
- 数据看板：成功指标实时数值（发帖、投票、意见、回访、DAU 估算）+ 近 7 天趋势

### 4.3 MVP 明确不做

分类/话题、积分等级、关注私信、搜索、图片上传、AI 对话、兴趣推荐算法、截止时间、举报之外的社交功能、多管理员角色权限。全部列入「验证成功后」清单。

## 5. 技术架构

### 5.1 总体

```
微信小程序 (uni-app + Vue3 + TS)
        │  HTTPS (api.xxx.com)
        ▼
Nginx ── 静态：管理后台 (Vue3 + Vite + Element Plus, admin.xxx.com)
        │
        ▼
API 服务 (Node.js + Express + Sequelize)
        │
        ▼
MySQL 8  （一台轻量云服务器 2C2G，PM2 守护）
```

- **用户端**：uni-app（Vue3 组合式 API）编译微信小程序；保留编译 H5 的能力（D14 对冲）
- **API**：Node.js 20 + Express，分层 routes / services / models，JWT（用户端用 openid 换 token）
- **管理后台**：Vue3 + Vite + Element Plus + Pinia + Vue Router
- **选型理由**：与开发者技能栈（Vue3）一致，作为求职作品三端齐全

### 5.2 关键流程

**登录**：小程序启动 `wx.login` → code 发后端 → 后端 code2Session 换 openid → 查/建 users → 签发 JWT。全程无感，不收集手机号/昵称/头像。

**发布**：提交 → 后端逐字段 msgSecCheck（标题、背景、选项文案）→ 全部通过：status=published；任一命中风险：status=pending（人工队列）。用户端「我的求助」显示对应状态。

**投票+意见**：`POST /votes`（postId + optionIndex + 可选 reason）；DB 唯一约束 `(post_id, user_id)` 防重复；reason 非空时先过 msgSecCheck；投票后返回最新比例。**先投票后意见**由接口顺序强制（无 vote 记录的 reason 请求直接拒绝）。意见点赞：`POST /votes/:id/like`，`vote_likes` 唯一约束一人一赞，重复请求幂等取消/恢复。

**回访**：node-cron 每日扫描 `published_at` 满 7 天且无 outcome 的帖子 → 调用微信订阅消息（一次性模板，发布成功页已授权）→ 用户点进回访页提交 → outcomes 落库 + 帖子状态更新。

**附近**：发帖时可选携带位置（wx.getLocation，授权失败可跳过）；MySQL 存 lng/lat，附近查询用经纬度矩形近似 + Haversine 排序（MVP 数据量不需要 GEO 索引）。降级方案见 D11。

**防刷**：一人一票（唯一约束）；发帖 ≤3/天、意见 ≤20/天（按 user 计数）；封禁用户拒写。

### 5.3 数据模型（MySQL）

```
users        id, openid(唯一), anon_no(如 #8264), status(正常/封禁), created_at
posts        id, user_id, title, background, status(审核中/已发布/已驳回/已下架),
             lng, lat, city(可空), vote_count, reason_count, view_count,
             created_at, published_at, rejected_reason(可空), removed_reason(可空)
post_options id, post_id, label, `desc`, sort, vote_count
votes        id, post_id, user_id, option_index, reason(可空), like_count, created_at
             UNIQUE KEY (post_id, user_id)
vote_likes   id, vote_id, user_id, created_at
             UNIQUE KEY (vote_id, user_id)   -- 意见点赞防重复
outcomes     id, post_id(唯一), user_id, chosen_index, content, created_at
reports      id, post_id, reporter_id, reason, status(待处理/已处理), created_at
admin_users  id, username, password_hash, created_at
events       id, user_id, type(pv/share_click/…), post_id(可空), created_at   -- 轻量埋点
```

### 5.4 部署与前置条件

- **ICP 备案（关键路径，1~2 周+）**：域名购买 → 个人备案 → 解析到服务器。**开发第 1 天并行启动**，备案期间联调用本地/测试环境
- HTTPS：Let's Encrypt 免费证书；小程序 request 合法域名 = api 域名
- 微信侧：小程序账号注册（个人）、类目（工具）、订阅消息模板申请、 getLocation 权限声明、隐私保护指引（位置用途、匿名承诺、不收集手机号）
- 服务器：轻量云 2C2G；PM2 守护 Node；Nginx 反代 + 管理后台静态托管

### 5.5 安全与合规清单

- 全部 UGC（帖子/意见/回访）过 msgSecCheck，风险内容人工复审
- 匿名承诺兑现：接口层不返回任何帖子的 user 归属（「我的」仅返回本人数据，靠 JWT）
- Wishbone 教训：openid 不落明文日志；管理后台强密码 + HTTPS；备份策略（每日 mysqldump）
- 个人主体类目风险：若被下架，uni-app 一键编译 H5 + 已备案域名承接，数据不动

## 7. 附：竞品与借鉴出处（背景参考）

- 钱包请等等（2026-10 爆火，30 万用户）：附理由投票、转发即求助的裂变机制
- 小红书「听劝」文化（篇均 43.9 条回复）：回访更新的行为验证（仅取行为，不取「劝」词汇）
- Reddit AITA / JuryNow：裁决感与陪审机制教训（无评论二选一不可解读、陪审员看不到结局=沉默虚空 → 我们让投票者可见回访）
- 小决定 Tiny Decisions：转盘兜底的刚需验证
- Wishbone（4000 万用户死亡的教训）：数据安全与无壁垒风险
